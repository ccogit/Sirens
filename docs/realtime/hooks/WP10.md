# WP10: Anschluss BeatGrid

WP31 ergänzt in `sirens/realtime/routes.py` nach der vorhandenen Origin- und
Feature-Flag-Prüfung **GET /api/rt/v1/assets/{id}/beatgrid**. Keine neuen
Dateipfade aus HTTP-Anfragen akzeptieren. Asset-ID via contracts.asset_id prüfen,
serverseitig auf registriertes Asset, validierten Quellpfad
(source_path/safe_audio_path) und tatsächliche Source-Samplerate auflösen.

- Beim expliziten Laden/Analysejob außerhalb des HTTP-Requests:
  `from .music_analysis import analyse_file, source_hash, CorrectionStore`
  dann `digest = source_hash(path)`, `info = analyse_file(path, asset_rate, configured_ffmpeg)`.
  Korrektur aus `CorrectionStore(cfg.rt_dir / "cache" / "beatgrid").load(digest, asset_rate)`
  bevorzugen. Store einmal pro Dienst instanziieren; Quellhash bei Änderung neu
  bilden; Pfad, Hash und Rate niemals blind vom Client übernehmen.
- GET liefert ausschließlich das gespeicherte Raster (Schema beatgrid, HTTP 200).
  Wenn kein sicheres Raster vorliegt, `raise error("unavailable")` (503); keine
  erfundene BPM. Unbekannte ID: not_found (404). Während Analyse ebenfalls 503.
  Keine Dekodierung, Hashberechnung oder Inferenz in GET.
- Korrekturen später über validierten expliziten UI-Befehl an
  `store.apply(digest, info["grid"], asset_rate, action, value)` leiten;
  Aktionen half/double, bar (ganze Schläge), phase (Quellframes), tap (mind. 3
  aufsteigende Quellframes). Ergebnis ersetzt das gecachte Raster atomar.
  Keine Korrektur-HTTP-Adresse ohne separaten Vertragsentscheid.
- Noten: nur vorhandene Basic-Pitch-JSON aus StemNoten.zustand verwenden,
  bei zustand bereit `notes_to_frames(info["noten"], asset_rate)`. Keine
  automatische Transkription, keine Modellbibliothek im Hauptprozess.
- Frontend: `createBeatGrid(grid, asset.sample_rate)` (beat_grid.js); Source-
  Frames erst über Clock/Transport in Output-Frames umsetzen. confidence < .5
  oder kein Raster: automatische Quantisierung deaktivieren. bar0 = Takt 0,
  beat0 = Schlag 0, feste 4/4-Annahme; tempo_map sortiert, stetige Schlagphase,
  Tempo gilt ab source_frame. nextBar liefert strikt nächste Samplegrenze.
- Key/Onsets/Sections sind separate Analysemetadaten, nicht Teil des
  eingefrorenen BeatGrid-Schemas. UI zeigt "unsicher" und manuelle Korrektur.
  Kein Schema oder Bestandsverhalten geändert.

Anpassungsbedarf: v1 kennt weder nullable BPM noch Downbeat-Konfidenz getrennt,
noch BeatGrid-Route im Protokoll. Unsichere Ergebnisse bleiben intern grid=null,
GET 503; separate Metadaten benötigen späteren Vertragsentscheid.

## Modelloption

`benchmarks/beatgrid/beat_this_manifest.json` ist das gesperrte Worker-Manifest
nach WP02; `BeatThisLiveStub` meldet keine Capability (probe=None), da v1
noch keine unbekannten Hop-/Kontext-/Latenzwerte darstellen kann. Nicht in
die Registry als nutzbare Capability aufnehmen. load/process/generate/warmup
lehnen mit unavailable ab. Freigabe erst nach geprüften Gewichten, Pins,
Worker-Implementierung und Messung, ohne automatischen Download.
